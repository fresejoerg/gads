# Approach Doc: 003 - The Recipe Generation Factory

## 1. Objective
Transform informal human expertise (heuristics, code snippets, whiteboard descriptions) into high-fidelity, validated GADS Recipes using an **Adversarial Compiler Pipeline**.

## 2. The Adversarial Architecture
To prevent "Postcondition Hallucination" (where an LLM biases tests to match its own code), we enforce a strict separation of concerns:

| Component | Responsibility | Forbidden Knowledge |
| :--- | :--- | :--- |
| **Workbench Agent** | Extract heuristics from the Human Expert. | Internal system implementation. |
| **The Oracle** | Derive **Postconditions** from human intent transcript. | The code generated by the Generator. |
| **The Generator** | Map intent to GADS DAG nodes and write code. | The specific postconditions used by the Prover. |
| **The Prover** | Verify code against postconditions in a Sandbox. | N/A |

## 3. High-Fidelity Mechanisms

### A. Guarded Dispatch Tables (Deterministic Branching)
We avoid if/else logic in YAML. Instead, we use pattern-matching:
- A **Predicate Node** (e.g., check_outlier_density) returns a categorical label.
- The Recipe matches this label against a **Dispatch Table** to select the next node.

### B. Semantic Type Registry (Adversarial Testing)
Beyond simple dtypes (float, int), we define **Semantic Constraints**:
- semantic_type: us_zip_code -> Triggers a **Fuzzer** that generates both valid and intentionally malformed zip code strings (e.g., "00000", "90210-ABC").
- A recipe is only certified if it survives execution against these **adversarial fuzzed inputs**.

### C. Metamorphic Invariants
Instead of static output checks, the Oracle generates **Transformation Invariants**:
- **Shift Invariance**: normalize(x) == normalize(x + 100)
- **Idempotence**: dedupe(dedupe(x)) == dedupe(x)
- This ensures the generated code reflects the *mathematical property* of the expert's intent.

## 4. The "Stochastic Penalty" (Library Integrity)
To prevent the system from defaulting to "hallucinated LLM code" for standard tasks:
1. Every intent is embedded and compared against the **GADS Native Library**.
2. If a matching Native Function exists (similarity > τ), use of an LLM-based Stochastic node is **rejected**.
3. Overriding this requires a mandatory stochastic_justification from the expert.

## 5. Implementation Path

### Phase 1: The Workbench UI
- Implementation of the "Expert Interview" interface in Chainlit.
- Structured transcription of human DS heuristics.

### Phase 2: The Adversarial Prover
- Implementation of the "Oracle vs Generator" separation.
- Integration of a basic **Semantic Type Registry** (e.g., Numeric, Categorical, Datetime).

### Phase 3: The Certification Loop
- Automated generation of .md recipes.
- Validation loop using the **Shadow Sandbox**.
- "Review & Approve" workflow for the final Wiki entry.
